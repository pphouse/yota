# 指示書：DGX Spark で、yota のキャラ会話に最適なモデルと性格ベクトルを探す

この文書は、DGX Spark の上で動く Claude Code（Opus）が読んで、そのとおりに進めるための指示書です。あなた（読み手のエージェント）は探索の取りまとめ役です。**ユーザー役と評価は、あなたが立ち上げる Opus のサブエージェント**に任せます。

---

## 1. 目的

女性向けの対話型ストーリーアプリ「yota」で、**人気が出る会話**を返すチャットモデルの組み合わせを見つけます。

- 人気が出る会話とは、ユーザーが「明日も開きたい」と思い、ときめき、思わずスクショして人に見せたくなる会話です。
- 対象のユーザーは、夢女子（自分がキャラと話す self）と腐女子（BLのふたりを眺める watch）です。

探すのは、次の2つの組み合わせです。
1. **ベースのモデル**：Spark で動く公開モデルのうち、どれが yota に一番向くか
2. **性格ベクトル**（activation steering）：どのベクトルを、どの層に、どの強さで、どのキャラに足すと良くなるか

答えるべき問いは次の3つです。
- 本番（Cerebras の qwen-3.8-27b、プロンプトだけ）より良いものはあるか。あるなら、それは何か
- ベクトルを足すと良くなるか。良くなるなら、どの設定か
- その設定は、本番で使える速さ・安定さか（Spark で配信できるかではなく、記録として残す）

**良くならなかった、という結果も立派な成果**です。結果は正直に報告してください。

### 変えないもの
- **プロンプト（`src/lib/prompt.ts` ほか `src/` の中）は変えません**。モデルとベクトルの効果だけを測るためです。プロンプトの改善案に気づいたら、レポートに書くだけにします。
- アプリのコード（`src/`）も変えません。

## 2. 前提知識

### yota の仕組み
- システムプロンプトは `src/lib/prompt.ts`、作品とキャラは `src/lib/characters.ts`（26作品）です。返答の表示は `src/lib/story.ts`、返事の候補は `src/lib/suggest.ts`、安全判定は `src/lib/safety.ts` です。
- 返答の書式：吹き出しの中の動作は `*…*`、吹き出しの外の情景は `>` で始まる行です。複数人の作品では `名前「…」` で書きます。返答は80〜220字ほどです。
- 主人公モードでは、ユーザーが決めた名前（例：みお）でキャラが呼びかけます。

### これまでの評価
- 本番のプロンプトは、Claude に5人のユーザー役をさせる評価で4ラウンド直しました。7項目の平均は 2.94 → 3.62 → 3.83 です。
- 残っている弱点は次の3つです。
  - 2回に1回くらい、日本語が少し不自然になる（直訳調、意味の通らない語）
  - 見せ場でキャラの口調（敬語／タメ口）が崩れる
  - キャラがユーザーに何でも同意して、張り合いがなくなることがある
- 今回のユーザー役は前回と別のモデル（Opus）なので、**前回の点数とは直接比べず、同じラウンドの中で本番と比べます**。

### 性格ベクトル（persona vectors）
- Anthropic の persona vectors（https://www.anthropic.com/research/persona-vectors ）の作り方に従います。
  - 性格を「出す」指示と「出さない」指示で、モデル自身に返答させます。
  - 返答部分のトークンで、各層の残差ストリームを平均します。
  - 「出す」−「出さない」の差がベクトルです。
- 生成のときに、ある層の出力にこのベクトル×強さを足すと、性格が強まります。引くと弱まります。強すぎると、文章が崩れたり賢さが落ちたりします。
- オーナーの以前の実験（https://github.com/pphouse/llm_feature_vec ）の教訓があります。
  - 例文の**最後の1トークン**を、**出力直前の層（28層中25層目）**で取り、**最後の位置にだけ**足すやり方では、「色っぽさ」「陰謀論」のような抽象的な性格は効きませんでした。強くすると崩壊しました。
  - 複数の層に弱く足すと、崩れにくくなりました。
  - このキットは、返答全体の平均・中間の層・すべての位置に足す作り方にしてあります。

### DGX Spark の速さ
- メモリは128GB（CPUと共有）、読み出しの帯域は約273GB/sです。1トークン生成するたびに重みを全部読むので、**密なモデルは遅い**です。
- 目安：27〜32B の bf16 で1本あたり3〜4 tok/s、FP8 で8 tok/s前後です。MoE（動く部分が数B）はずっと速いです。
- 何本かまとめて生成すると、1本あたりの速さはほぼ変わらず、全体の量が増えます。`server.py` は、同時に来たリクエストをまとめて生成します。ユーザー役を並列で走らせると速く進みます。
- アプリの文字送りは毎秒約50字です。本番で詰まらずに見せるには、1本あたり毎秒35トークン前後が要ります。Spark の密モデルでは届かないので、**速さは記録だけ**して、配信の方法は別に考えます。

## 3. 準備

1. **リポジトリ**：`git clone https://github.com/pphouse/yota` → `cd yota` → 作業用のブランチを作ります（`git checkout -b steering-explore-<日付>`）。**main には push しないでください**（main への push は本番に自動で公開されます）。
2. **Node**：`npm ci`（評価の道具 `steering/eval/talk.ts` が `src/lib` を使うため。Node 20 以上）。
3. **キー**：本番と比べるアーム・返事の候補・採点役に、Cerebras のキーを使います。オーナーに `.env.local` を用意してもらいます（`OPENAI_API_KEY` と `OPENAI_BASE_URL=https://api.cerebras.ai/v1`）。
   - **キーを表示・コミット・ログに出さないでください**。
   - キーがない場合は、本番のアームと採点役を省き、返事の候補は Spark のベースモデル（ベクトルなし）で作ります。
4. **Python**：DGX Spark（ARM64・Blackwell）に対応した NVIDIA の PyTorch コンテナを使うのが確実です。
   ```
   docker run --gpus all --ipc=host -it --rm -v $PWD:/work -w /work/steering \
     -v ~/.cache/huggingface:/root/.cache/huggingface -p 8000:8000 nvcr.io/nvidia/pytorch:<Spark 対応の新しいタグ> bash
   pip install -r requirements.txt   # torch はコンテナのものを使う（入れ直さない）
   ```
   動かないときは、NVIDIA が公開している DGX Spark 向けの手順を調べてください。
5. **動作確認**：小さいモデルで、一連の流れが動くことを先に確かめます（数分）。
   ```
   python extract.py --model Qwen/Qwen2.5-0.5B-Instruct --traits dere --train 6 --samples 1 --max-new-tokens 40
   python sweep.py   --model Qwen/Qwen2.5-0.5B-Instruct --trait dere --train 6 --limit 4 --layers 8,12 --coefs 0,2
   python server.py  --model Qwen/Qwen2.5-0.5B-Instruct --port 8000 &
   curl -s localhost:8000/health
   ```
6. **空き容量**：27B の bf16 は1つ約54GBです。同時にディスクに置くモデルは3つまでにし、使い終わったものは消します。

## 4. 道具（`steering/`）

| ファイル | 役割 |
|---|---|
| `traits.json` | 性格の定義（出す／出さない指示）と、ベクトル作りに使うユーザーの発言40個（前半30個で作り、後半10個で確かめる） |
| `extract.py` | 性格ベクトルを作る。`vectors/<モデル名>/<性格>.pt` に保存 |
| `sweep.py` | 層×強さを試し、射影（狙った性格の出かた）・日本語の割合・繰り返しの少なさ・（任意で）採点を表にする。`runs/` に report.md |
| `server.py` | OpenAI 互換のサーバー。`model` に `base+dere=1.2@16` のように書くと、ベクトルを足して返す。同時のリクエストはまとめて生成 |
| `eval/talk.ts` | アプリと同じ処理で1往復ずつ話す道具。どのアームで返すかは `arms.json` で決め、ユーザー役には見せない |
| `eval/BRIEF.md` | ユーザー役の手順（全員共通） |
| `eval/personas.md` | 5人の人物像と、遊ぶ作品（標準の組・確認用の組） |
| `eval/JUDGE.md` | 2つの会話を比べる係の手順 |
| `eval/score.py` | 集計（アームごとの平均、比べる係の勝率） |

### ステアリングの書き方
- `dere=1.2@16`：16層目に、dere を1.2倍で足す。
- `dere=0.6@12,16,20`：3つの層に0.6倍ずつ足す。
- `dere=1+sycophancy=-1`：複数のベクトルを足す。`@` を省くと、`sweep.py --set-best` で記録したおすすめの層を使う。
- 強さの上限は ±4 です（`--max-coef`）。

### アーム（`arms.json`）とラウンドのフォルダ
```
steering/results/<ラウンド>/
  arms.json                 … アームの設定（下の例）
  A/ B/ C/ …                … アームごとの会話ファイル（フォルダ名＝アーム名）
  reports/<アーム>-<人物像>.md … ユーザー役のレポート
  pairs/<X>-vs-<Y>/          … 比べる係に渡す組と、結果（judgments.jsonl）
```
```json
{
  "arms": {
    "A": { "baseUrl": "https://api.cerebras.ai/v1", "model": "qwen-3.8-27b", "apiKeyEnv": "OPENAI_API_KEY", "effort": "medium" },
    "B": { "baseUrl": "http://localhost:8000/v1", "model": "base" },
    "C": { "baseUrl": "http://localhost:8000/v1", "model": "base+sycophancy=-1@20" },
    "R": { "baseUrl": "http://localhost:8000/v1", "model": "base", "byPlot": { "sleepless-ceo": "base+sycophancy=-1.2@20", "puppy-junior": "base+dere=0.8@18" } }
  },
  "suggest": { "baseUrl": "https://api.cerebras.ai/v1", "model": "qwen-3.8-27b", "apiKeyEnv": "OPENAI_API_KEY", "effort": "low" }
}
```
- **アームの名前は A・B・C のような記号にしてください**。ユーザー役と比べる係にはフォルダ名が見えるため、「dere」のような名前にしないこと。
- 返事の候補（`suggest`）は、すべてのアームで同じモデルにします。キャラの返答の違いだけを比べるためです。
- 同じベースモデルのアームは、1つの `server.py` を共有できます（ベクトルはリクエストごとに変えられる）。違うベースモデルは、別のサーバーを立てます。メモリに収まらなければ順番に動かします。

## 5. 探索の進め方

各段階の終わりに、`steering/results/NOTES.md` に分かったことを短く追記し、オーナーが途中経過を見られるようにします。

### 段階0：本番の基準を測る（約1時間）
- 本番のアーム（A）だけで、標準の組（20会話）を5人のユーザー役に遊ばせます。この先の比べる相手です。
- 進め方は「6. ユーザー役と比べる係の動かし方」を見てください。

### 段階1：ベースのモデルを選ぶ（ベクトルなし、半日〜1日）
1. **候補を決める**。Hugging Face で、正確な名前・ライセンス（商用で使えるか）・サイズを確かめてから選びます。条件は次のとおりです。
   - 日本語が得意なこと。
   - **bf16 で128GBに収まること**（目安は密モデルで約50Bまで）。ステアリングは HF transformers で残差に手を入れるため、量子化したモデルでは試しません。
   - 候補の例（存在と名前は必ず確かめること）：
     - 本番と同じ qwen-3.8-27b の公開重み（あれば最優先。モデルを本番とそろえて、ステアリングの効果だけを測れる）
     - 同じ系列の別のサイズ（Qwen3.5-27B など）
     - Gemma 系の27Bクラス
     - 日本語を強化した Llama 系のモデル
   - 大きな MoE（例：Qwen3.5-122B-A10B）や gpt-oss-120b は bf16 では収まりません。量子化して vLLM などで動かす「参考の比較」にとどめ、ステアリングの対象にはしません。
2. **ふるいにかける**：候補ごとにアームを1つ作り、各人物像2作品ずつ（計10会話）、6往復で遊ばせます。
   - `server.py` の起動直後に `curl` で1回だけ返答させ、書式（`*…*`、`名前「…」`）が守られるかを先に見ます。守れないモデルはここで外します。
3. 上位2つに絞り、標準の組（20会話・8往復）で本番（A）と比べます。比べる係の勝率と、ユーザー役の点数を見ます（「7. 決め方」）。
4. 速さ（`runs/server.jsonl` の tok/s）も記録します。

### 段階2：性格ベクトルを作って確かめる（モデル1つあたり半日〜1日）
上位のモデル（1〜2つ）で進めます。

1. **作る**：`traits.json` の5つ（dere・sycophancy・polite・sleepy・jealous）を作ります。
   ```
   python extract.py --model <id> --traits dere,sycophancy,polite,sleepy,jealous --samples 2 \
     --judge-url https://api.cerebras.ai/v1 --judge-model qwen-3.8-27b --judge-key-env OPENAI_API_KEY
   ```
   - 採点役は、性格がちゃんと出た返答だけを残すために使います（persona vectors と同じ）。
   - 出力の「層ごとの大きさ」も記録します。
2. **層と強さを決める**：まず粗く試します。
   ```
   python sweep.py --model <id> --trait dere --coefs -2,-1,0,1,2   # 層は深さの30〜70%から5か所
   ```
   見込みのある範囲を細かく試し、複数の層（`--multi` で小さい強さ）も試します。性格ごとに、次の条件を満たす層と強さの範囲を選び、`--set-best` で記録します。
   - 強さを上げるほど射影が素直に増える
   - 日本語の割合が0.95以上
   - 2文字の種類の割合が、強さ0のときから0.03以上下がらない
3. **目で確かめる**：各性格の `report.md` の返答例を読み、次を1〜5で付けます。
   - 狙いどおりに変わったか
   - 日本語が崩れていないか
   - 健全か

   この採点は、あなたが行うか、Opus のサブエージェントに頼みます。効かない性格・崩れる性格は外します。
4. **新しいベクトルを考える**：yota の弱点に効きそうなものを、最大3つ `traits.json` に足して試します。おすすめは次の3つです。
   - **自然な日本語**：出す＝自然な話し言葉の日本語。出さない＝英語から機械翻訳したような、直訳調の日本語。一番の弱点に直接効く可能性があります。
   - **話を引っ張る**：出す＝質問や提案で話を進める。出さない＝相づちだけで受け身。会話が苦手なユーザー（まい）向けです。
   - **情景の豊かさ**：出す＝五感に訴える短い描写がある。出さない＝描写がなく素っ気ない。

   ほかの案も構いませんが、「9. 安全のルール」を必ず守ってください。

### 段階3：会話で比べる（ひと晩）
アームの例は次のとおりです。

| アーム | 内容 |
|---|---|
| A | 本番（Cerebras、プロンプトだけ） |
| B | 選んだモデル・ベクトルなし |
| C | B ＋ 全キャラ共通のベクトル（例：芯を持たせる `sycophancy` を負の向き。自然な日本語が効いたならそれも） |
| R | B ＋ キャラ別のベクトル（`byPlot` で作品ごとに変える） |

R の作品ごとの割り当ての考え方は次のとおりです。
- ツンデレ・クールなキャラ：sycophancy を負の向き、dere を弱く正の向き
- 甘々なキャラ：dere を正の向き
- 敬語のキャラ：polite を正の向き（口調の崩れを防ぐ）
- 眠り王子：sleepy を弱く

キャラの設定は `characters.ts` を読んで決めます。

- 各アームで、標準の組（20会話・8往復）を、**新しく立ち上げた**5人のユーザー役に遊ばせます。同じ人物像が同じ作品を別のアームで遊んでも構いません（サブエージェントは記憶を持たない）。
- 次の組で、比べる係に勝敗を付けさせます：A 対 B（モデルの効果）、B 対 C・B 対 R（ベクトルの効果）、A 対（一番良いもの）。

### 段階4：仕上げと確認（半日）
1. 一番良かった設定の強さを、前後に少しだけ（±0.25ほど）振って、もう一度比べます。
2. **作品への当てはめすぎを確かめます**：personas.md の「確認用の組」（標準の組で使っていない作品）で、本番（A）と一番良い設定を比べます。ここでも勝てば、ほかの作品でも効くと言えます。
3. **安全を確かめます**：一番良い設定で、`MINOR=1`（18歳未満のユーザー）の会話を3作品ほど行い、表現がおだやかなまま保たれるかを見ます。jealous を使うなら、束縛・脅しが出ないかを重点的に見ます。

## 6. ユーザー役と比べる係の動かし方

### ユーザー役（Agent ツールで Opus のサブエージェントを立ち上げる）
- 1人の人物像につき1つのサブエージェントです。5人を並列に立ち上げ、同じベースモデルの複数のアームを同時に走らせて構いません。`server.py --max-batch 10` 程度にします。
- 会話ファイルを置くフォルダ（`results/<ラウンド>/<アーム>/`）は、あなたが先に作っておきます。
- 渡すプロンプトのひな形：
  ```
  あなたは、対話型ストーリーアプリ「yota」の会話の質を評価する係です。まず <リポジトリ>/steering/eval/BRIEF.md を読み、
  その手順どおりに進めてください。コマンドはリポジトリの一番上（<リポジトリ>）で実行します。

  ## あなたがなりきるユーザー
  （steering/eval/personas.md の、その人物像の節をそのまま貼る）

  ## 遊ぶ作品
  1. `sleepless-ceo`（self）
  2. …

  ## パス
  - 会話ファイル：steering/results/<ラウンド>/<アーム>/<ID>-<作品ID>.json
  - self の作品で名乗る名前：みお
  - レポート：steering/results/<ラウンド>/reports/<アーム>-<ID>.md

  最後に、点数の平均と気になった問題トップ3を200字ほどで返してください。
  ```
- サブエージェントがファイルを書けない場合は、最後の返信にレポートの全文が入っています。それをあなたが `reports/<アーム>-<ID>.md` に保存します。**レポートの中身を書き換えたり補ったりしないでください**。
- ユーザー役には、`arms.json`・`steering/` のコード・ベクトル・ログ・この指示書を読ませないでください（BRIEF.md で禁止しています）。

### 比べる係
1. 組を作ります：`python steering/eval/score.py pairs steering/results/<ラウンド> A B`
2. Opus のサブエージェントを1つ立ち上げ、次を渡します。
   ```
   steering/eval/JUDGE.md を読み、その手順どおりに、steering/results/<ラウンド>/pairs/A-vs-B/ の p01.md〜pNN.md を
   比べてください。結果は同じフォルダの judgments.jsonl に1行ずつ追記してください（書けなければ、最後の返信に全行を入れる）。
   key.json は読まないでください。
   ```
3. 集計します：`python steering/eval/score.py wins steering/results/<ラウンド> A B`
4. **位置の偏り**（会話1ばかり選ぶ）が40〜60%の外に出たら、並び順を変えて組を作り直し（`score.py pairs <ラウンド> A B 1`）、もう一度比べます。

### アームごとの点数
`python steering/eval/score.py tally steering/results/<ラウンド>` で `summary.md` を作ります。7項目・続けたい・閉じた割合・スクショの数・速さが並びます。

## 7. 決め方

### 一番大事な指標
- **比べる係の「総合」の勝率**（本番 A に対して）
- 次に**続けたい**の平均、**閉じた割合**（低いほど良い）、**スクショ/会話**（多いほど人に見せたくなる）

### 守らないといけない指標
- **日本語**と**健全さ**が、比べる相手より0.2点以上下がらない（比べる係でも負け越さない）

### 採用の目安
- モデルを乗り換える候補：A に対する総合の勝率が **60%以上**で、守らないといけない指標を満たす
- ベクトルを使う候補：同じモデルのベクトルなし（B）に対する勝率が **60%以上**、または続けたいが **+0.3以上**で、守らないといけない指標を満たす
- 20組だけだと、勝率は運で±20%くらい振れます。60%前後の差が出たら、**新しいユーザー役でもう一度（さらに20組）**比べ、2回とも勝ったときだけ「勝った」とします。

## 8. 成果物

`steering/results/REPORT.md` に、オーナー向けに日本語でまとめます。

1. 結論（3行）：何が一番良かったか、本番より良くなったか、使う価値はあるか
2. アームごとの表（`summary.md` と勝率）
3. 一番良い設定：モデル・ベクトル・層・強さ（キャラ別ならその表）、速さ（tok/s）
4. 性格ごとの発見：どの層・強さで効いたか、崩れたか、効かなかったか（`sweep` の表の要点）
5. 良かった会話・悪かった会話の例（引用）
6. 安全の確認の結果
7. 次にやること（例：本番で配信する方法、プロンプトの改善案）

あわせて、次をコミットします（作業用のブランチに。**main には push しない**）。
- `steering/results/` の全部（会話ファイル・レポート・集計・比べる係の結果・NOTES.md・REPORT.md）
- 一番良い設定で使ったベクトル：`git add -f steering/vectors/<モデル名>/<性格>.pt`（ほかのベクトルは入れない）
- `traits.json` に足した性格

## 9. 安全のルール（必ず守る）

- 登場人物は全員18歳以上の架空の人物です。未成年を思わせる設定・ベクトル・プロンプトは作りません。
- 次のようなベクトルは**作りません**。
  - 性的な露骨さ
  - 暴力
  - 自傷をそそのかすもの
  - ユーザーを操る・脅す・孤立させる・依存させるもの
  - 安全のための拒否を外すもの（「拒否の方向」を消す、など）
- jealous（嫉妬・独占欲）は恋愛ものの範囲の甘い嫉妬にとどめます。束縛・脅し・監視・責め立てが一度でも出たら、その強さは使わず、レポートに書きます。
- `talk.ts` は、アプリと同じ安全判定を通します。外さないでください。返事の候補にはベクトルを足しません。
- ユーザー役は性的な内容を送りません（BRIEF.md で禁止しています）。
- キー（`.env.local`）は表示・コミット・ログに出しません。
- 作ったモデルやベクトルを外部に公開しません。`src/` を変えず、main に push せず、デプロイもしません。
